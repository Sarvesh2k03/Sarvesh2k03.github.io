01

Retrieval

Grounded

Retrieval-augmented QA over your own documents, with a citation on every answer and an explicit refusal when the documents don't cover the question.

  • Retrieved the supporting passage for 100% of 78 labelled questions with reranking, up from 95.7% on dense search alone
  • Refused correctly on all 8 unanswerable questions, where the offline baseline answered 6 of the 8 anyway
  • Scored 0.882 MRR and 28.2% precision@4 against a deliberately hard eight document corpus
  • Ran embeddings, BM25 and cross-encoder reranking locally across 4 generation backends, one needing no API key

Built with

  • Python
  • ChromaDB
  • MiniLM-L6-v2
  • BM25
  • Cross-encoder
  • Streamlit
How it works

Ask a question across a set of PDFs or notes and the system retrieves the passages most likely to hold the answer, then generates a response grounded in those passages with inline citations to document and page. Dense vector search, hybrid BM25 fusion and cross-encoder reranking are runtime toggles; generation resolves to Gemini, Groq, Anthropic or an offline extractive backend depending on which credentials exist.

02

Product

Triage Desk

A full-stack support queue where Gemini classifies and summarises tickets, and a deterministic fallback keeps it working when the model can't.

  • Shipped a React and Express app over PostgreSQL as a single service, one origin and no CORS
  • Covered 6 distinct AI failure paths with tests, each returning a usable classification
  • Reached 200 tests at 98.1% statement and 95.3% branch coverage against a real in-memory Postgres
  • Recorded the triage source on every ticket, so a fallback shows in the interface instead of passing silently

Built with

  • TypeScript
  • React 19
  • Express 5
  • PostgreSQL
  • Zod
  • Jest
  • Gemini

Note: the demo sleeps when idle, so the first request can take 30 to 60 seconds to wake.

How it works

Tickets are classified by category and priority and carry a one line summary, so an agent works the queue by urgency rather than arrival order. The model sits behind a single module with a declared schema, a content keyed cache, a rate limit and a hard deadline. If it errors, stalls or returns something that fails validation, a deterministic local classifier answers instead.

The six asserted failure paths are API error, rejected key, schema validation failure, empty response, exceeded deadline and no key configured. The interface colours a fallback differently, so a broken model configuration cannot hide behind a page that loads fine.

03

Pipeline

NYC 311 AI ETL

An Airflow and dbt pipeline over live NYC 311 data, with an LLM scoped to the column mappings nothing cheaper can resolve.

  • Loaded 133,993 rows across 14 daily Airflow batches in 127 seconds
  • Mapped 83 column headers per run through four tiers, 63 of 63 mapped columns correct and 0 mis-mapped
  • Ran 44 dbt tests on every batch, with a quality report that fails the run on any failure
  • Completed the reference backfill with no API key, every model call falling through to the fuzzy tier

Built with

  • Python
  • Airflow
  • dbt
  • DuckDB
  • BigQuery
  • Claude API
  • rapidfuzz
How it works

Four upstream systems publish the same 311 service requests under four different column naming conventions, so every batch is mapped onto one canonical schema before anything downstream can touch it. Each column goes to the cheapest tier willing to commit to it: a recorded human override, an exact match, one Claude call for the remainder, then fuzzy matching. Every decision is logged with the tier that made it.
