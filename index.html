AI that
holds up

I build AI systems that turn messy real-world data into decisions people can rely on — then prove they still work when the model doesn't.

Most of what I've learned came from watching models fail in public. At a Mumbai startup I replaced a wall of brittle regex with a Llama 4 Scout extractor that turned messy WhatsApp threads into structured JSON. At NUS I trained a custom YOLO pose model to 87% accuracy — the highest recorded for that architecture on the task — and deployed it. For a steel manufacturer I built demand forecasting and a custom logistics optimiser.

Every one hit the same wall: getting good output from a model is the easy half. The engineering is everything around it — what the system does when the model is slow, rate-limited or confidently wrong, and how anyone would know. That's what the three projects below are about.

The work

Built,
then broken

Anyone can show you a demo on a good day. So each of these three carries a drop test: the failure I induced on purpose, and what the system did about it. Removing the source document. Pulling the API key mid-session. Running a fourteen-day backfill with no credentials at all.

The demo is the easy half. What follows is the half I'd want to be asked about.

01

Retrieval

Grounded

Answers that cite their sources — and an "I don't know" when the sources don't cover the question.

Every retrieval demo I tried answered confidently even when the answer wasn't in the documents. This one is built for the opposite failure. Chunking, embeddings, BM25 and reranking run locally; generation resolves to whichever backend has credentials, down to a fully offline extractive fallback. Each answer carries citations to document and page, and the interface separates the passages it actually used from the ones it merely retrieved.

02

Product

Triage Desk

A support queue where the AI is an upgrade, never a dependency.

A support queue is a bad place for a model to be load-bearing. So the ticket workflow is complete on its own — create, filter, update, resolve — and Gemini only adds a category, a priority and a one-line summary for the agent. The model call lives behind a single module with a schema, a cache, a rate limit and a hard deadline. React and Express in TypeScript over Postgres, shipped as one service so there's one origin and nothing to negotiate.

03

Pipeline

NYC 311 AI ETL

An LLM inside a nightly pipeline, scoped to the thirteen columns nothing cheaper can resolve.

The same 311 payload arrives from four systems that each name their columns differently. Fuzzy matching handles the easy ones and quietly gets meaning wrong on the rest — assignedAgencyLabel scores 0.90 against agency_code, which is the wrong field, and no threshold separates them because the difference is meaning, not spelling. So each column goes to the cheapest tier that will commit to it: a human override, an exact match, one Claude call for the remainder, then fuzzy. Every decision is logged with the tier that made it.

Method

House
rules

The same five decisions turn up in all three projects, in the same order. This is the part I'd defend in a design review — and the reason the numbers above exist at all.

01

Decide what happens without the model, first.

Before I write a prompt I write the version that has no model in it. That's what makes the AI safe to add — and it means I can tell you what the model is actually worth, because I've run the system both ways.

Proof: the 311 reference run — 133,993 rows, 44 tests — completed with no API key configured at all.

02

Make the model commit to a shape, then check the meaning.

Free text is not an interface. Every call returns structured JSON against a declared schema, validated before anything touches a database — and validated for sense, not just syntax. A proposal naming a field that doesn't exist becomes a caught error instead of a corrupted column.

Proof: six distinct AI-failure paths under test in Triage Desk, all six returning a usable classification.

03

Measure against ground truth, not vibes.

"Seems accurate" is not a result. Writing down the true column mapping turned accuracy into arithmetic — which is how I know the cheap tier is 100% precise on what it commits to, and exactly which 13 columns need an LLM. That number is the argument for the LLM tier, and the reason it's scoped to those 13.

Proof: Grounded's harness reports precision@k, evidence recall@k, MRR, abstention accuracy and hallucination rate.

04

Put the degradation where someone can see it.

A silent fallback is a bug wearing a feature's clothes — the page loads, the answer looks fine, and a broken model configuration survives to production. So the interface says which engine answered, and an answer that isn't in the documents comes back as a refusal rather than a paraphrase.

Proof: ticket records its triage source and the panel changes colour; Grounded marks cited passages separately from merely retrieved ones.

05

Leave it reproducible, including the bad news.

Every figure here comes from a command in a README. That includes the findings I'd rather not advertise — the 17 backdated requests are documented next to the test that caught them. Work that can't be re-run is a claim, not a result.

Proof: make backfill · npm run test:coverage · python -m grounded.evaluate — and two of the three repos run with no API key.

Working with AI

Building with LLMs is part of the skill set, and I treat it with the same discipline as building on them. I use models to move fast — scaffolding, refactors, a second opinion on a schema at midnight — and then make them argue against the result: read this as a staff engineer and tell me which claim isn't backed by anything. That loop is genuinely fast, and it is not a substitute for knowing why the architecture is shaped the way it is.

I made the design calls, ran the pipelines, and produced every number here. Where AI helped, it helped the way it does in these projects — with a check on the output and a human accountable for what ships.
