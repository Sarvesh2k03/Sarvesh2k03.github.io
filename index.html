01

The trust problem

Grounded

Can a RAG system admit that it doesn't know?

Why I built it. Every retrieval demo I tried answered confidently even when the answer wasn't in the documents. I wanted the opposite failure mode — refuse, and show the passages behind every answer it does give.

What it is. Question answering over your own PDFs, Markdown and text. Chunking, embeddings, BM25, rank fusion and cross-encoder reranking all run locally; generation resolves to whichever backend has credentials — Gemini, Groq, Anthropic, or a fully offline extractive fallback. Every answer carries inline citations down to the document and page, and the interface marks which retrieved passages the answer actually used versus which it merely had available.

Try this in the demo. Ask who first walked on the Moon. Then deselect the Apollo Missions document in step 1 and ask again — the same question now returns "I don't know based on the provided documents" instead of assembling something plausible from the other six.

02

The product problem

Triage Desk

What happens to the app when the model times out?

Why I built it. A support queue is a bad place for an AI feature to be load-bearing. So the ticket workflow is complete on its own — create, filter, update, resolve — and Gemini only improves it: category, priority, and a one-line summary for the agent.

What it is. A full-stack support desk. React and Express in TypeScript over Postgres, deployed as a single service so there is one origin and no CORS negotiation between halves. The model call is isolated behind one module, its output validated with Zod, cached by content, rate-limited and deadlined.

The part I care about. When Gemini is missing, slow, blocked, or returns a payload that fails validation, a deterministic local classifier answers instead and the ticket records which one did it. The UI colours a fallback differently — amber instead of blue — so a broken model configuration can't hide behind a page that loads fine.

03

The scale problem

NYC 311
AI ETL

Can an LLM sit inside a nightly pipeline without becoming a single point of failure?

The problem. The same 311 payload arrives from four upstream systems that each name their columns differently. Fuzzy string matching gets the easy ones and quietly gets meaning wrong on the rest: assignedAgencyLabel scores 0.90 against agency_code, and that is the wrong field. No threshold separates those cases, because the difference is meaning, not spelling.

What it does. Each column is resolved by the cheapest tier willing to commit to it — human override, exact match, one Claude call for everything left, fuzzy fallback — and every decision is logged with the tier that made it. Two guardrails earn their place: only one column may claim a canonical field, and if a required key doesn't resolve, the task fails loudly rather than loading a table with a hole in it. Airflow runs it daily, dbt builds the marts, and a quality report fails the run on any failed test.

The measurement. The reference run below was produced with no API key configured. Every LLM call failed to authenticate and fell through to the fallback — the auth failure recorded in the run's quality report — and the pipeline completed normally.

One real finding: a test failed on the first full run — 17 requests were stamped closed exactly 72 hours before they were created. Upstream backdating in the live feed. They aren't dropped (they're real requests and still count as volume) and they aren't let through (six negative durations would drag down every SLA average). They're flagged and their resolution time nulled, with a warning test keeping the rate visible on every run.
