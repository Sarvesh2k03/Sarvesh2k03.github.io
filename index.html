AI that
holds up

I build AI systems that turn messy real-world data into decisions people can rely on — then prove they still work when the model doesn't.

Most of what I've learned came from watching models fail in public. At a Mumbai startup I replaced a wall of brittle regex with a Llama 4 Scout extractor that turned messy WhatsApp threads into structured JSON. At NUS I trained a custom YOLO pose model to 87% accuracy — the highest recorded for that architecture on the task — and deployed it. For a steel manufacturer I built demand forecasting and a custom logistics optimiser.

Every one hit the same wall: getting good output from a model is the easy half. The engineering is everything around it — what the system does when the model is slow, rate-limited or confidently wrong, and how anyone would know. That's what the three projects below are about.

From trust
to scale

Three projects, and each one starts where the last one stopped. First: can I trust what an AI tells me? Then: what happens to the product when it stops answering? Finally: can it run on a schedule, over real data, without becoming the thing that breaks?

All three are live. All three are open source. Every number below comes from a command in the repo.

01

Trust

Grounded

Retrieval-augmented QA with citations

It started with a question I couldn't get a straight answer to: how do you know a RAG system isn't making it up? Every demo I tried answered confidently even when the answer wasn't in the documents. So I built one designed for the opposite failure — refuse, and show the passages behind every answer it does give.

Try this: ask who first walked on the Moon, then deselect the Apollo Missions document and ask again. The same question comes back "I don't know based on the provided documents" instead of a plausible answer assembled from the other six.

  • Ingests PDF, Markdown and text with page numbers preserved, so every citation points somewhere real
  • Three retrieval strategies — dense vector search, hybrid BM25 fusion, and cross-encoder reranking — switchable at runtime
  • Four generation backends resolved from whatever credentials exist, including one that runs fully offline
  • Evaluated on precision@k, MRR, abstention accuracy and hallucination rate, with paired bootstrap p-values on every comparison
  • Python
  • ChromaDB
  • MiniLM-L6-v2
  • BM25
  • Cross-encoder
  • Streamlit

02

Resilience

Triage Desk

Support queue with a tested fallback

Once I could trust the output, the next question was what happens when there isn't any. A support queue is a bad place for an AI feature to be load-bearing — so the ticket workflow is complete on its own, and Gemini only improves it with a category, a priority and a one-line summary for the agent.

Before you click: the demo runs on Render's free tier, which sleeps after 15 minutes idle — the first request can take 30–60 seconds to wake it. Once it's up, /api/health reports whether AI triage is actually enabled.

  • Full-stack ticket workflow that works with the AI switched off — React 19, Express 5, PostgreSQL, one service, one origin
  • The model call is isolated behind a single module: schema-validated JSON, content-keyed cache, rate limit and hard deadline
  • 200 tests at 98.1% statement and 95.3% branch coverage, run against a real in-memory Postgres so a bad column name fails the test
  • Six AI-failure paths asserted — timeout, refusal, rejected key, invalid schema, empty response, no key at all — each returning a usable answer
  • Every ticket records which engine triaged it, and the panel changes colour when it wasn't the model
  • TypeScript
  • React 19
  • Express 5
  • PostgreSQL
  • Zod
  • Jest
  • Gemini

03

Scale

NYC 311
AI ETL

AI-assisted schema mapping in production

Then I wanted to know whether an LLM could sit inside something that runs on a schedule without becoming the thing that breaks it. The same 311 payload arrives from four systems that each name their columns differently — and fuzzy matching quietly gets meaning wrong: assignedAgencyLabel scores 0.90 against agency_code, which is the wrong field. No threshold separates those, because the difference is meaning, not spelling.

One real finding: a dbt test failed on the first full run — 17 requests stamped closed exactly 72 hours before they were created, upstream backdating in the live feed. They're flagged and their resolution time nulled rather than dropped, with a warning test keeping the rate visible on every run.

  • 133,993 rows of live NYC 311 data loaded across 14 daily Airflow batches in 127 seconds
  • 83 column headers resolved per run through four tiers — human override, exact match, one Claude call, fuzzy fallback — each decision logged with the tier that made it
  • 100% mapping precision (63/63) and 0 columns mis-mapped, measured against a written-down ground truth rather than asserted
  • 44 dbt tests across staging, intermediate and mart layers; a quality report fails the run on any failure
  • The reference run was produced with no API key — every LLM call failed to authenticate, fell through to the fallback, and the pipeline completed normally
  • Python
  • Airflow
  • dbt
  • DuckDB
  • BigQuery
  • Claude API
  • rapidfuzz

| Method |

How I
build

The same five decisions turn up in all three projects, in the same order. This is the part I'd defend in a design review — and the reason the numbers above exist at all.

01

Decide what happens without the model, first.

Before I write a prompt I write the version that has no model in it. That's what makes the AI safe to add — and it means I can tell you what the model is actually worth, because I've run the system both ways.

Proof: the 311 reference run — 133,993 rows, 44 tests — completed with no API key configured at all.

02

Make the model commit to a shape, then check the meaning.

Free text is not an interface. Every call returns structured JSON against a declared schema, validated before anything touches a database — and validated for sense, not just syntax. A proposal naming a field that doesn't exist becomes a caught error instead of a corrupted column.

Proof: six distinct AI-failure paths under test in Triage Desk, all six returning a usable classification.

03

Measure against ground truth, not vibes.

"Seems accurate" is not a result. Writing down the true column mapping turned accuracy into arithmetic — which is how I know the cheap tier is 100% precise on what it commits to, and exactly which 13 columns need an LLM. That number is the argument for the LLM tier, and the reason it's scoped to those 13.

Proof: Grounded's harness reports precision@k, evidence recall@k, MRR, abstention accuracy and hallucination rate.

04

Put the degradation where someone can see it.

A silent fallback is a bug wearing a feature's clothes — the page loads, the answer looks fine, and a broken model configuration survives to production. So the interface says which engine answered, and an answer that isn't in the documents comes back as a refusal rather than a paraphrase.

Proof: ticket records its triage source and the panel changes colour; Grounded marks cited passages separately from merely retrieved ones.

05

Leave it reproducible, including the bad news.

Every figure here comes from a command in a README. That includes the findings I'd rather not advertise — the 17 backdated requests are documented next to the test that caught them. Work that can't be re-run is a claim, not a result.

Proof: make backfill · npm run test:coverage · python -m grounded.evaluate — and two of the three repos run with no API key.

Building with LLMs is part of the skill set, and I treat it with the same discipline as building on them. I use models to move fast — scaffolding, refactors, a second opinion on a schema at midnight — and then make them argue against the result: read this as a staff engineer and tell me which claim isn't backed by anything.
